# Role and permission matrix

This matrix contains the broader authorization target from the HUKMEE brief; rows beyond the active API are requirements, not proof of implementation. The Prisma auth model now follows Constructor's direct `User.roleId` and `Role.permissions` layout. Active roles are `SUPER_ADMIN`, `ADMIN`, `USER`, `VENDOR`, `WORKER`, and `DELIVERY_PARTNER`. Existing technician-facing HUKMEE routes accept the `WORKER` account role for compatibility.

The active routes do enforce selected guards: `USER` role for profile/address operations and booking ownership checks; `TECHNICIAN` for assignment decisions/inspection/estimates; `bookings:manage` for manual assignment/eligible-tech listing; `inventory:manage` for inventory reads. The development seed grants `inventory:manage`, `bookings:manage` and other listed permissions to both `ADMIN` and `SUPER_ADMIN`; there is no hub-scoped inventory permission. This does not implement the full target matrix below.

| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `USER`                                     | Own profile, addresses, devices, bookings, assigned-vendor tracking, estimate decisions, payments/invoices, repair/warranty history, complaints                                                   | No cross-user access; user ownership checked in each resource query.                                                                                                         |
| `WORKER` (technician-facing HUKMEE routes) | Own permitted profile/duty, offered or assigned jobs, acceptance/rejection, arrival/evidence/inspection, authorized estimates, parts requests/returns, repair progression, own permitted earnings | Cannot approve own KYC, alter payment, inventory balance, commission or financial ledger. `booking.view_assigned`, `booking.accept`, `estimate.submit`, `inventory.request`. |

## Enforcement requirements

For every protected endpoint, authenticate the account, check action permission, then check resource ownership/assignment/hub scope. Role names alone are insufficient where data scope differs. Reject client attempts to set protected fields such as role, approval, payment verification, stock balance, commission, warranty activation or final job status.

Role assignment, permission mapping, KYC decisions, payment/refund, inventory movement, state override and settlement changes require audit records. Where separation of duties applies, enforce it in the service transaction, not only in UI or route middleware.

## Implementation sequence

1. Seed named permissions and role mappings idempotently; define controlled operator provisioning.
2. Add route/action guards and shared ownership/assignment/hub-scope query helpers.
3. Add denial and cross-resource tests before exposing domain endpoints.

Do not migrate role values or broaden admin access until impacted records and callers have been reviewed.
