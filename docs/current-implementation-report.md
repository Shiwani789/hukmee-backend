No active route accepts image/file uploads: Express is configured for JSON, and no mounted router uses multipart handling.

Legacy upload snippets are not API contracts: banner code names a single `image` field; review code declares up to five `images`; vendor admin code names a single `documentUrl`; KYC controller contains `req.file`/`req.files` code and also accepts a client-provided `documentUrl`, but no KYC route is present. ## Recommended implementation order and next-module acceptance criteria

The approved SOW is not available, so priorities below follow the pasted scope, existing requirements matrix, schema and open decisions. No new write workflow in these areas was safe to implement: each requires missing schema/provider support or unresolved authorization/policy. The safe technician self-service read endpoints are listed above; the existing active partial write workflows are retained.

1. **Recommended next module: KYC/onboarding design approval, then implementation.** Confirm required documents by persona/jurisdiction, reviewer permissions/separation of duties, bank verification, retention and private storage before adding schema or routes. Use `TECHNICIAN` for the existing vendor/technician persona; do not create a duplicate `VENDOR` account role. Keep worker and delivery-partner KYC distinct only if release requirements confirm those personas.
2. Payments/provider workflow: approve provider, payment amount/currency source, timing, callback signature/idempotency, refund rules and finance authority; then implement and test against provider sandbox credentials.
3. Inventory writes: approve hub-scoped permissions, movement semantics/approvals, negative-stock behavior and an idempotency mechanism. Existing movement schema has no idempotency key, so safe retryable writes require schema approval before API work.
4. Repair/QC/warranty: approve repair transitions, payment/parts gates, evidence and QC checklists, no-part exception, warranty terms and claim rules; configure private object storage before media endpoints.
5. Automated matching: approve service areas, distance/ranking, availability/capacity, retries/timeouts and override authority. Existing manual assignment is the safe supported workflow until then.
6. Notifications: approve event triggers, consent/preferences, content/locales, retry/retention behavior and providers; approve persistence/outbox schema before delivery APIs.
7. Verify the current OpenAPI/Postman response examples in a configured client environment, and run DB-backed tests only against an already-migrated dedicated `*_test` database.

**Recommended next module acceptance criteria (KYC, conditional on approval):** (a) no second VENDOR login/role is introduced; current `TECHNICIAN` persona is used for the vendor/technician business actor, while worker/delivery-partner KYC remains separate if confirmed. (b) required documents and fields come from approved jurisdiction/persona configuration; no document types are assumed. (c) private upload storage validates approved file constraints, stores object references rather than public URLs, and enforces approved retention/access rules. (d) applicant ownership, authenticated reviewer permission, separation of duties, submission/review/rejection/resubmission history and audit events are enforced transactionally. (e) technician assignment eligibility cannot be granted by client-supplied status and reads only approved KYC state. (f) tests cover valid submissions, missing documents, unauthorized access, forbidden self-review, rejected/resubmitted records, private-field masking and storage/provider failure. (g) no production data/migration until an approved schema change and a dedicated migrated test database are available.
